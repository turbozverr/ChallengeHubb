5.1 Smart Use Case diagram
Smart Use Cases. Вона забезпечує єдиний візуальний контекст для всієї екосистеми ChallengeHub, включаючи мобільний застосунок для користувачів та веб-платформу для адміністрації та бізнес-партнерів.
Весь функціонал розміщено всередині єдиної межі «Система ChallengeHub», що відокремлює внутрішню логіку від зовнішніх акторів.
Основні актори гість, користувач, бізнес-клієнт, адмін, модератор, які ініціюють взаємодію, розташовані ліворуч. Другорядні актори, зовнішні сервіси Google API, Stripe API, Gemini API розміщені праворуч, оскільки вони лише обслуговують запити системи.
Для наочності складності функцій використано різні рівні деталізації.

Кожна оцінка підкріплена функціональною логікою, описаною в розділі Major Features документа Vision & Scope.
Мета створення таблиці:
Визначення сумарного обсягу робіт для розрахунку швидкості розробки команди.

Використання балів як лінійної міри для відстеження прогресу виконання проекту.

5.3 Class diagram
Рисунок 5.3 - Діаграма класів для веб та мобільного застосунку
User: Представляє основного користувача мобільного додатка, який взаємодіє з платформою, створює власний контент та виконує челенджі для отримання досвіду (XP).
WebUser: Базовий клас для всіх користувачів, які мають доступ до адміністративної панелі через веб-інтерфейс; містить загальну логіку авторизації.
Admin: Спеціалізована роль для повного керування платформою, включаючи налаштування системних лімітів, перегляд глобальної аналітики та управління ролями користувачів.
Moderator: Користувач, відповідальний за перевірку контенту на відповідність правилам спільноти та розгляд скарг (Reports) на відео чи профілі.
BusinessClient: Партнер платформи, який фінансує спонсорські кампанії, створює маркетингові челенджі та аналізує результати активностей для просування бренду.
Challenge: Базова сутність, що описує завдання, правила його виконання, рівень складності та кількість досвіду, що нараховується за успішне завершення.
SponsoredChallenge: Розширений тип завдання, що створюється бізнес-клієнтами; може містити додаткові винагороди у вигляді промокодів та брендований контент.
Video: Медіа-контент, який користувач завантажує як доказ виконання челенджу; проходить стадію модерації перед публікацією в загальну стрічку.
Comment: Текстове повідомлення, залишене користувачем під відеозвітом або іншим елементом контенту для соціальної взаємодії.
Notification: Системне або персоналізоване повідомлення, що інформує користувача про події (наприклад, нове завдання, отримання бейджа або коментар).
Badge: Елемент гейміфікації, який користувач отримує за виконання певних умов, досягнення рівнів або активність у системі.
Subscription: Модель надання преміум-можливостей користувачу на певний термін; керує статусом доступу до розширеного функціоналу.
Transaction: Фінансова операція в системі, що фіксує оплату підписки або фінансування спонсорської кампанії бізнес-клієнтом.
Report: Об'єкт, що містить інформацію про порушення (причина, посилання на контент) та використовується модераторами для прийняття рішень.
Leaderboard: Сервісний клас, що відповідає за формування та відображення рейтингу користувачів на основі їхньої активності та накопиченого досвіду.
AI_Assistant: Інтелектуальний модуль, який аналізує поведінку користувача, рекомендує челенджі та надсилає мотиваційні повідомлення.
SystemSettings: Глобальні параметри платформи, такі як пороги автоматичної модерації, ліміти скарг та конфігурація параметрів ШІ.

Опис діаграми об'єктів мобільного застосунку (Mobile App Snapshot)
Діаграма об'єктів мобільного клієнта відображає стан системи в конкретний момент часу, демонструючи взаємодію кінцевого користувача з ігровими та соціальними механіками платформи:
Профіль користувача та підписка: Екземпляр denys класу User має активний статус та пов'язаний зв'язком subscription з об'єктом proSub класу Subscription. Це підтверджує наявність плану "Premium", що дає користувачу доступ до розширеного функціоналу. Його прогрес також відображається через зв'язок appearsIn у глобальному рейтингу weeklyBoard класу Leaderboard.
Активність у челенджах та контент: Об'єкт denys бере участь (participation) у челенджі fitness30 класу Challenge. Доказом виконання завдання є завантажений користувачем об'єкт video777 класу Video (зв'язок uploads), який логічно належить до цього випробування (relatedTo). За свої досягнення користувач отримав (earns) об'єкт marathoner класу Badge.
Робота AI-помічника та сповіщення: Екземпляр aiGemini класу AI_Assistant взаємодіє з користувачем через рекомендації контенту та відправку (sends) об'єкта notif15 класу Notification. Ця нотифікація типу "ChallengeReminder" відображається як отримана користувачем (receives).
Соціальна взаємодія: Користувач maksym класу User виступає автором (writes) об'єкта comment89 класу Comment, який структурно прикріплений (attachedTo) до відеозвіту Дениса.
Опис діаграми об'єктів веб-платформи (Web Platform Snapshot)
Ця діаграма фіксує стан веб-інтерфейсу системи ChallengeHub, фокусуючись на адміністративних процесах, фінансовій взаємодії з бізнес-клієнтами та модерації контенту:
Бізнес-логіка та монетизація: Екземпляр brandEva класу BusinessClient ініціює фінансовий потік, створюючи (creates) об'єкт payment402 класу Transaction. Ця транзакція є джерелом фінансування (funds) для рекламної кампанії evaPromo класу SponsoredChallenge. Бізнес-клієнт має повний контроль над керуванням (manages) цим челенджем.
Модерація та обробка скарг: На діаграмі відображено процес реагування на порушення правил спільноти. Спонсорський челендж містить (contains) об'єкт video99 класу Video, на який надійшла скарга. Це згенерувало об'єкт report102 класу Report, який опрацьовує (handles) екземпляр modRoman класу Moderator. Модератор отримує сповіщення про необхідність перевірки через об'єкт alert102 класу Notification та здійснює безпосередній перегляд контенту (reviews).
Системне адміністрування: Об'єкт adminMykola класу Admin здійснює нагляд (supervises) за роботою модератора та керує конфігурацією системи через об'єкт globalSettings класу SystemSettings. Налаштування визначають глобальні параметри, такі як ліміти скарг та пороги модерації. Також показано вплив спонсорського контенту на стан об'єкта weeklyBoard класу Leaderboard (зв'язок affects).
